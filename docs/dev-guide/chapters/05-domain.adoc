== Domain

=== Bounded contexts

[cols="1,2,2",options="header"]
|===
|Context |Runs as |Argo tool that matters
|Payments |long-running service |Argo CD, Argo Rollouts
|Settlement |batch: runs and exits |Argo Workflows, Argo Events
|===

=== Entities (keep it to five)

[cols="1,3,1",options="header"]
|===
|Entity |Key fields |Owner
|`Merchant` |id, name, settlementCurrency |Payments
|`Payment` |id, merchantId, amount, currency, status, createdAt |Payments
|`AcquirerRecord` |bankRef, merchantId, paymentId?, amount, valueDate |Settlement (from bank file)
|`SettlementBatch` |id, businessDate, status, totals per merchant |Settlement
|`Discrepancy` |batchId, merchantId, type (`MISSING`, `DUPLICATE`, `AMOUNT_MISMATCH`), paymentId?, bankRef? |Settlement
|===

`Payment.status`: `AUTHORIZED -> CAPTURED -> REFUNDED`, or `DECLINED`.
Use Java records for `AcquirerRecord` and `Discrepancy`; JPA entities only in payment-api.

=== payment-api

[cols="2,3",options="header"]
|===
|Endpoint |Purpose
|`POST /payments` |authorize -> `AUTHORIZED` or `DECLINED`
|`POST /payments/{id}/capture` |capture
|`POST /payments/{id}/refund` |refund
|`GET /payments?businessDate=YYYY-MM-DD` |ledger export (CSV) for the settlement job
|`GET /actuator/health/{liveness,readiness}` |Kubernetes probes
|`GET /actuator/prometheus` |metrics, e.g. `payments_requests_total{outcome}`
|===

* PostgreSQL + Flyway; virtual threads on (`spring.threads.virtual.enabled=true`).
* *Fault injection:* `FAULT_RATE` (0.0–1.0) makes that share of requests return HTTP 500.
  Ship a version with `FAULT_RATE=0.3` and watch the canary analysis roll it back.
* A small load generator keeps traffic flowing so the analysis has data.

=== settlement-job

One jar, one image; the step is chosen by argument so every workflow step runs the same image.

[cols="1,2,2",options="header"]
|===
|Step |Input |Output
|`--step=fetch` |bank file (input *artifact* from MinIO) |`records.json` artifact, *output parameter* `merchants` (JSON list)
|`--step=ledger` |`businessDate` parameter, calls payment-api |`ledger.csv` artifact
|`--step=match` |`merchantId` + both artifacts |`discrepancies-<id>.json`, parameter `count`
|`--step=report` |all discrepancy artifacts |`settlement-report.csv`, parameter `totalDiscrepancies`
|`--step=alert` |`totalDiscrepancies` |log line / webhook call
|===

Exit code `0` = success, non-zero = failed step (this is what drives retries).
`FLAKY=true` makes `ledger` fail now and then to practise `retryStrategy`.

=== The nightly workflow

[source,mermaid]
----
flowchart LR
  F[fetch bank file] --> M{{match per merchant<br/>fan-out withParam}}
  L[export ledger] --> M
  M --> R[build report]
  R -->|when totalDiscrepancies > 0| A[alert]
  R -.->|onExit| X[exit handler: record batch status]
----

* `fetch` and `ledger` run in parallel: no dependency between them.
* `match` fans out with `withParam: "{{tasks.fetch.outputs.parameters.merchants}}"`.
* `alert` has a `when` condition; the `onExit` handler runs whatever happens.
* `ledger` has `retryStrategy` (limit 3, backoff).

=== How things start and ship

Workflow triggers::
. *Argo Events* (primary): MinIO `EventSource` on bucket `acquirer-files`,
  `s3:ObjectCreated:*` -> `Sensor` -> submit from the `WorkflowTemplate` with `fileKey`.
. *CronWorkflow* (fallback): 02:30 Europe/Istanbul, yesterday's date.
. *Manual*: `argo submit --from workflowtemplate/settlement -p businessDate=...`

payment-api releases (Rollouts)::
`setWeight 20 -> analysis (success rate >= 99% for 2m) -> setWeight 50 -> pause 2m -> 100`.
Without a mesh the weight is approximated by replica count. Second exercise: blue-green with
a preview service and `prePromotionAnalysis`.

Deployment (Argo CD)::
Root app-of-apps; sync waves `-1` platform, `0` apps, `1` workflow/event resources;
`ApplicationSet` (list generator) for dev and prod; auto-sync with prune + self-heal on dev,
manual on prod; `PostSync` smoke-test hook; an `AppProject` limiting repos and namespaces.

=== Out of scope

Real card schemes, PCI, ISO 8583, OAuth, FX, any UI.
